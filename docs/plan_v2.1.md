## 2. 接口约定（直接照此联调）

### 2.1 WS63 板端 → PC（UDP 上报，核心新增）

板子只接 5V 电源，连入同一手机热点（2.4 GHz 频段），向 PC 局域网 IP 的 **UDP `9001` 端口**发送原始雷达帧，以下两种格式任选其一（PC 端均已兼容）：

**格式 A（推荐，直接复用现有串口日志格式）：**
```text
[RADAR_SAMPLE] gear=2 rng=1.85 vel=-1.20 snr=18.5 hm=1
```

**格式 B（JSON）：**
```json
{"gear": 2, "rng": 1.85, "vel": -1.20, "snr": 18.5, "human": 1}
```

> **板端约定**：板子只发原始采样帧，跌倒规则判定仍在 PC 端跑；WiFi 断线后固件每 3 s 自动重连。

### 2.2 PC 服务端事件格式（严格保持 9 字段不变）

```json
{"device_id":"cam-1","t_ms":12840,"frame_id":642,"state":"suspect",
 "action":"fall","reason":"fast_then_still","rng":0,"vel":0,"human":1}
```

- `device_id` 分三路：`cam-1`（摄像头）、`ws63-1`（雷达）、`fusion-1`（融合仲裁最终输出）。
- 网页接口：`POST /api/events`、`GET /api/state`、`GET /api/events/stream`（SSE）、`GET /video/cam-1`（实时骨骼画面 MJPEG）、`POST /api/reset`（复位报警）。

### 2.3 融合仲裁口径

- **双确认**：2 s 窗口内 `cam-1` 和 `ws63-1` 均进入 `suspect/alarm` → `fusion-1` 立即升级 `alarm`（`reason=fusion_confirmed`）。
- **雷达否决**：`cam-1` 报 `suspect/alarm`，但 `ws63-1` 在线且为 `normal` → `fusion-1` 压在 `suspect` 不升级，记 `[VETO]` 日志（用于抑制“主动躺沙发”误报）。
- **超时降级**：超过 5 s 未收到 `ws63-1` UDP 包 → 自动切换为 `DEGRADED`，由 `cam-1` 单独负责报警，记 `[DEGRADED]` 日志。
- **遮挡兜底**：摄像头 `human=0` 且雷达报 `suspect` → 输出 `suspect`（`reason=radar_occluded_fallback`）。

## 4. 现场联调与采数的硬性注意点（避坑）

1. **硬件摆放防干扰**：WS63 是 2.4 GHz 感知雷达，若后续使用 WiFi 摄像头，**摄像头和 WS63 至少隔开 30–50 cm**，禁止贴身绑在一起，否则 2.4 GHz 视频流会把雷达 `snr` 打崩。
2. **摄像头机位统一**：架在 **1.5–2 m 高处略向下斜俯视**，人与镜头距离 **2–3 m**，确保人站立和躺地全身都在画面内；避免强逆光或对着屏幕反光翻拍。
3. **测试跌倒停留时间**：按当前规则，真跌倒测试需在倒地后保持静止 **至少 9–10 秒**，才能完整走完 `normal → suspect (3 s) → alarm (8 s)` 全链路（后续可按答辩需求额外加“演示快速模式 1 s / 3 s”开关）。
4. **先测通信再测算法**：WS63 烧完固件后，先在 PC 上跑 `python -m pc.udp_source` 确认终端持续打印雷达包，再启动 `start.bat` 做双模联调。
